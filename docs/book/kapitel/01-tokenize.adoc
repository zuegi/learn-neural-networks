[[Tokenize]]
== Tokenize

Ein Tokenizer zerlegt Rohtext (Sätze, Wörter, Satzzeichen) in kleinere Einheiten, sogenannte Tokens, und ordnet diesen stabile numerische IDs zu. Dieser Schritt ist notwendig, weil Modelle mit Zahlen arbeiten, nicht mit Zeichenketten.

=== Konzept

Zum Verständnis bauen wir einen einfachen, regelbasierten Tokenizer auf Basis einer Regex. Er erzeugt aus einem Rohtext ein Vokabular mit stabilen IDs.
Er erkennt:

* Wörter mit Apostroph, typografischem Apostroph, Bindestrich und Unterstrich
* einfache Satzzeichen
* die Special Tokens `<|unk|>` und `<|endoftext|>`

`encode` tokenisiert neuen Text mit derselben Regelbasis und mappt unbekannte Tokens auf die ID von `UNKNOWN`.
`decode` übersetzt IDs zurueck in Tokens und setzt sie mit einfachen Spacing-Regeln wieder zu Text zusammen.
Zusätzlich hät die Klasse ein Reverse-Mapping `idToToken` bereit und ergaänzt `UNKNOWN` sowie `ENDOFTEXT` immer am Ende des Vokabulars.

Die Map `idToToken` wird direkt aus `vocab` abgeleitet:

* vocab.entries liefert alle Einträge des Vokabulars als Map.Entry<String, Int>
* { (token, id) -> ... } destrukturiert jeden Eintrag in token (Key) und id (Value)
* id to token erzeugt ein Pair<Int, String> – also genau umgekehrt zur ursprünglichen Zuordnung
* associate { ... } baut daraus eine neue Map<Int, String>

Ergebnis: Aus {"the" -> 42, "cat" -> 17} wird {42 -> "the", 17 -> "cat"}.

*Zusammengefasst*: Fuer die Tokenisierung braucht es `vocab` (Text -> IDs), fuer die Rueckuebersetzung `idToToken` (IDs -> Text).

=== Beispiel: Roundtrip mit bekannten Tokens

Erster Beweis: Fuer bekannte Tokens gilt Roundtrip.
Wenn alle Tokens im Vokabular enthalten sind, dann liefert `decode(encode(text))` wieder den Originaltext.

[source,kotlin]
----
val rawText = "Darling, do you like water?"
val tokenizer = SimpleTokenizerV1(rawText)
val text = "Darling, do you like water?"

val ids = tokenizer.encode(text)
val decoded = tokenizer.decode(ids)
val isEqual = decoded == text

println("text: $text")
println("ids: $ids")
println("decoded: $decoded")
println("roundtrip.equal: $isEqual")
----

Erwartete Ausgabe:
[source, terminaloutput]
----
text: Darling, do you like water?
ids: [0, 1, 2, 3, 4, 5, 6]
decoded: Darling, do you like water?
roundtrip.equal: true
----

Interpretation:

* Alle Tokens sind bekannt (`Darling`, `,`, `do`, `you`, `like`, `water`, `?`).
* Deshalb geht keine Information beim Encodieren verloren.
* `decode(encode(text)) == text` ist `true`.

=== Beispiel: Unbekannte Tokens sauber nachweisen

Aus `rawText = "Darling, do you like water?"` wird das Vokabular aufgebaut.
Danach wird `"Hello, do you like tea?"` encodiert.
Die Woerter `Hello` und `tea` kommen im Vokabular nicht vor und werden deshalb auf `UNKNOWN` gemappt.

Aus dem `rawText` entstehen diese 7 Tokens:

1. Darling
2. ,
3. do
4. you
5. like
6. water
7. ?

[source, kotlin]
----
val rawText = "Darling, do you like water?"
val tokenizer = SimpleTokenizerV1(rawText)
val text = "Hello, do you like tea?"
val idList: List<Int> = tokenizer.encode(text)
println("idList.size: ${idList.size}")
println("idList: $idList")
println("Vokabular.size: ${tokenizer.vocabSize}")
println("Vokabular: ${tokenizer.vocab}")
println("decoded: ${tokenizer.decode(idList)}")
----

Erwartete Ausgabe:
[source, terminaloutput]
----
idList.size: 7
idList: [7, 1, 2, 3, 4, 7, 6]
Vokabular.size: 9
Vokabular: {Darling=0, ,=1, do=2, you=3, like=4, water=5, ?=6, <|unk|>=7, <|endoftext|>=8}
decoded: <|unk|>, do you like <|unk|>?
----

Die Vokabulargroesse ist 9, weil nach den 7 Tokens aus dem `rawText` zwei Konstanten ergaenzt werden:

[source,kotlin]
----
const val UNKNOWN = "<|unk|>"
const val ENDOFTEXT = "<|endoftext|>"
----

Interpretation des Nachweises:

* ID `7` ist `UNKNOWN`
* `7` kommt in `idList` genau fuer `Hello` und `tea` vor
* `decode(idList)` macht das sichtbar als `<|unk|>, do you like <|unk|>?`

Damit ist das Verhalten von `encode` und `decode` fuer unbekannte Tokens konsistent gezeigt.

=== Design-Entscheidungen

* **Regelbasiert statt gelernt:** Fokus auf Nachvollziehbarkeit und reproduzierbare Ergebnisse.
* **Stabile IDs mit LinkedHashMap:** Reihenfolge folgt dem ersten Auftreten im Trainings-/Rohtext.
* **UNKNOWN statt Fehler:** Unbekannte Eingaben bleiben verarbeitbar; Pipeline bricht nicht.
* **ENDOFTEXT nicht automatisch anfuegen:** Keine implizite Semantik; nur explizite Tokens werden encodiert.
* **Einfache Spacing-Regeln in `joinTokens`:** Gut lesbare Rueckuebersetzung ohne komplexen Detokenizer.

=== Stolpersteine

* **Regex-Details:** Kleine Aenderungen in der Regex aendern Token-Grenzen stark.
* **Gross-/Kleinschreibung:** `Hello` und `hello` sind unterschiedliche Tokens.
* **Unicode-Apostrophe:** `'` und `’` muessen beide sauber erkannt werden.
* **Satzzeichen als eigene Tokens:** Spacing bei `decode` braucht explizite Regeln.
* **Spezial-Tokens im Text:** `<|unk|>` und `<|endoftext|>` muessen vor allgemeinen Wortregeln erkannt werden.

=== Byte Pair Encoding
In den GPT Modellen werden aber weit effizientere Tokenizer verwendet, als der von uns entwickelte SimpleTokenizerV1.
Das Konzept für diese Tokenizer nennt sich `Byte Pair Encoding`. Ein BPE zerlegt ebenso wie unser SimpleTokenizer den Text in Bruchteile von Wörtern (Subword), indem er iterativ die im Trainingskorpus am häufigsten vorkommenden benachbarten Zeichenpaare sucht und zu einem neuen, gemeinsamen Token zusammenfügt, bis eine gewünschte Vokabulargröße erreicht ist.
Einen BPE Tokenizer zu implementieren ist aufwändig und kompliziert. Deshalb werden wir einen Open-Source BPE Tokenizer namens link:https://jtokkit.knuddels.de/[JTokkit].

Auch wenn wir diesen Tokenizer nur für unseren Wissensaufbau für das Erstellen einer LLM (die nie einen produktiven Charakter ausweisen wird), ist es schon auffällig, dass die JVM Community den Trend für die LLMS verschlafen oder schon wieder aufgegeben haben.
Auch das JTokkit Framework wird seit ca 2 Jahren kaum mehr gepflegt. Im Gegensatzu dazu die Python tiktoken Implementierung die immer noch aktiv weiter entwickelt wird.
Wie wir noch sehen werden sind viele gute Absichten Code Komponenten, die für das Bilden einer LLM notwendig sind, zu entwicklen wieder auf Eis gelegt worden
