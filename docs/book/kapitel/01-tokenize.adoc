[[Tokenize]]
== Tokenize

Ein Tokenizer zerlegt Rohtext (Sätze, Wörter, Satzzeichen) in kleinere Einheiten, sogenannte Tokens, und ordnet diesen stabile numerische IDs zu. Dieser Schritt ist notwendig, weil Modelle mit Zahlen arbeiten, nicht mit Zeichenketten.

=== Konzept

Zum Verständnis bauen wir einen einfachen, regelbasierten Tokenizer auf Basis einer Regex. Er erzeugt aus einem Rohtext ein Vokabular mit stabilen IDs.
Er erkennt:

* Wörter mit Apostroph, typografischem Apostroph, Bindestrich und Unterstrich
* einfache Satzzeichen
* die Special Tokens `<|unk|>` und `<|endoftext|>`

`encode` tokenisiert neuen Text mit derselben Regelbasis und mappt unbekannte Tokens auf die ID von `UNKNOWN`.
`decode` übersetzt IDs zurück in Tokens und setzt sie mit einfachen Spacing-Regeln wieder zu Text zusammen.
Zusätzlich hält die Klasse ein Reverse-Mapping `idToToken` bereit und ergänzt `UNKNOWN` sowie `ENDOFTEXT` immer am Ende des Vokabulars.

=== Warum ein Tokenizer?

Ein Sprachmodell kann nicht direkt mit Zeichenketten arbeiten.
Bevor aus Text Embeddings, Attention oder Training entstehen können, muss der Text daher in eine numerische Repräsentation überführt werden.

Genau das leistet ein Tokenizer:

* Er zerlegt Text in kleinere Einheiten.
* Er ordnet diesen Einheiten stabile IDs zu.
* Er schafft damit die Brücke zwischen Rohtext und Modellinput.

Die Map `idToToken` wird direkt aus `vocab` abgeleitet:

* vocab.entries liefert alle Einträge des Vokabulars als Map.Entry<String, Int>
* { (token, id) -> ... } destrukturiert jeden Eintrag in token (Key) und id (Value)
* id to token erzeugt ein Pair<Int, String> – also genau umgekehrt zur ursprünglichen Zuordnung
* associate { ... } baut daraus eine neue Map<Int, String>

Ergebnis: Aus {"the" -> 42, "cat" -> 17} wird {42 -> "the", 17 -> "cat"}.

*Zusammengefasst*: Für die Tokenisierung braucht es `vocab` (Text -> IDs), für die Rückübersetzung `idToToken` (IDs -> Text).

=== Beispiel: Roundtrip mit bekannten Tokens

Ein erster Nachweis zeigt den einfachsten Fall: Alle Tokens sind bekannt.
Dann liefert `decode(encode(text))` wieder den ursprünglichen Text.

[source,kotlin]
----
val rawText = "Darling, do you like water?"
val tokenizer = SimpleTokenizerV1(rawText)
val text = "Darling, do you like water?"

val ids = tokenizer.encode(text)
val decoded = tokenizer.decode(ids)
val expectedIds = listOf(0, 1, 2, 3, 4, 5, 6)
val isEqual = decoded == text

println("text: $text")
println("ids: $ids")
println("decoded: $decoded")
println("expectedIds: $expectedIds")
println("roundtrip.equal: $isEqual")

check(ids == expectedIds)
check(isEqual)
----

Erwartete Ausgabe:
[source, terminaloutput]
----
text: Darling, do you like water?
ids: [0, 1, 2, 3, 4, 5, 6]
decoded: Darling, do you like water?
roundtrip.equal: true
----

Interpretation:

* Alle Tokens sind bekannt (`Darling`, `,`, `do`, `you`, `like`, `water`, `?`).
* Deshalb geht keine Information beim Encodieren verloren.
* `ids` wird zusätzlich gegen die erwartete Liste `listOf(0, 1, 2, 3, 4, 5, 6)` geprüft.
* `decode(encode(text)) == text` ist `true`.

=== Beispiel: Unbekannte Tokens sauber nachweisen

Aus `rawText = "Darling, do you like water?"` wird das Vokabular aufgebaut.
Danach wird `"Hello, do you like tea?"` encodiert.
Die Wörter `Hello` und `tea` kommen im Vokabular nicht vor und werden deshalb auf `UNKNOWN` gemappt.

Aus dem `rawText` entstehen diese 7 Tokens:

`["Darling", ",", "do", "you", "like", "water", "?"]`

[source, kotlin]
----
val rawText = "Darling, do you like water?"
val tokenizer = SimpleTokenizerV1(rawText)
val text = "Hello, do you like tea?"
val idList: List<Int> = tokenizer.encode(text)
val expectedIds = listOf(7, 1, 2, 3, 4, 7, 6)
val expectedDecoded = "<|unk|>, do you like<|unk|>?"
val decoded = tokenizer.decode(idList)

println("idList.size: ${idList.size}")
println("idList: $idList")
println("Vokabular.size: ${tokenizer.vocabSize}")
println("Vokabular: ${tokenizer.vocab}")
println("decoded: $decoded")
println("expectedIds: $expectedIds")
println("expectedDecoded: $expectedDecoded")

check(idList == expectedIds)
check(decoded == expectedDecoded)
check(tokenizer.vocabSize == 9)
----

Erwartete Ausgabe:
[source, terminaloutput]
----
idList.size: 7
idList: [7, 1, 2, 3, 4, 7, 6]
Vokabular.size: 9
Vokabular: {Darling=0, ,=1, do=2, you=3, like=4, water=5, ?=6, <|unk|>=7, <|endoftext|>=8}
decoded: <|unk|>, do you like<|unk|>?
----

Die Vokabulargröße ist 9, weil nach den 7 Tokens aus dem `rawText` zwei Konstanten ergänzt werden:

[source,kotlin]
----
const val UNKNOWN = "<|unk|>"
const val ENDOFTEXT = "<|endoftext|>"
----

Interpretation des Nachweises:

* ID `7` ist `UNKNOWN`
* `7` kommt in `idList` genau für `Hello` und `tea` vor
* `idList` wird explizit gegen `listOf(7, 1, 2, 3, 4, 7, 6)` geprüft
* `decode(idList)` macht das sichtbar als `<|unk|>, do you like<|unk|>?`

Damit ist das Verhalten von `encode` und `decode` für unbekannte Tokens konsistent gezeigt.

=== Design-Entscheidungen

* **Regelbasiert statt gelernt:** Fokus auf Nachvollziehbarkeit und reproduzierbare Ergebnisse.
* **Stabile IDs mit LinkedHashMap:** Reihenfolge folgt dem ersten Auftreten im Trainings-/Rohtext.
* **UNKNOWN statt Fehler:** Unbekannte Eingaben bleiben verarbeitbar; Pipeline bricht nicht.
* **ENDOFTEXT nicht automatisch anfügen:** Keine implizite Semantik; nur explizite Tokens werden encodiert.
* **Einfache Spacing-Regeln in `joinTokens`:** Gut lesbare Rückübersetzung ohne komplexen Detokenizer.

=== Stolpersteine

* **Regex-Details:** Kleine Änderungen in der Regex ändern Token-Grenzen stark.
* **Groß-/Kleinschreibung:** `Hello` und `hello` sind unterschiedliche Tokens.
* **Unicode-Apostrophe:** `'` und `’` müssen beide sauber erkannt werden.
* **Satzzeichen als eigene Tokens:** Spacing bei `decode` braucht explizite Regeln.
* **Spezial-Tokens im Text:** `<|unk|>` und `<|endoftext|>` müssen vor allgemeinen Wortregeln erkannt werden.

=== Byte Pair Encoding
In GPT-Modellen werden deutlich effizientere Tokenizer verwendet als der von uns entwickelte `SimpleTokenizerV1`.
Das zugrunde liegende Konzept heißt `Byte Pair Encoding`.

Ein BPE zerlegt den Text ebenfalls in Bruchteile von Wörtern (`Subwords`).
Dazu werden im Trainingskorpus häufig vorkommende benachbarte Zeichenpaare schrittweise zu gemeinsamen Tokens zusammengeführt, bis eine gewünschte Vokabulargröße erreicht ist.

Einen BPE-Tokenizer von Grund auf selbst zu implementieren ist aufwändig.
Deshalb verwenden wir hier die Open-Source-Bibliothek link:https://jtokkit.knuddels.de/[JTokkit].

Dieses Kapitel verfolgt ein Lernziel und keinen produktiven Einsatz.
Dabei zeigt sich eine praktische Herausforderung im JVM-Umfeld: Einige LLM-Bausteine werden langsamer weiterentwickelt als in Python-Ökosystemen.
Auch JTokkit wird derzeit weniger aktiv gepflegt, während https://github.com/openai/tiktoken[tiktoken] in Python weiterhin stark weiterentwickelt wird.
Für den Nachbau bedeutet das: Manche Komponenten sind nutzbar, andere erfordern Anpassungen, Workarounds oder alternative Bibliotheken.

Im Folgenden betrachten wir, wie wir dieses Encoding mit JTokkit in unser Projekt einbinden.

==== Warum JTokkit

Wir verwenden JTokkit, weil es OpenAI-kompatible Encodings für die JVM bereitstellt.

* JTokkit liefert OpenAI-kompatible BPE-Tokenisierung für Java/Kotlin.
* Entscheidend ist die Encoding-Wahl; in diesem Kapitel nutzen wir `r50k_base` (Ada-nah).
* `encode`/`decode` bilden Text und Token-IDs konsistent ineinander ab; `encodeOrdinary` behandelt Special Tokens als normalen Text.
* Damit sparen wir Implementierungsaufwand für Merge-Regeln, Vokabularverwaltung und Byte-Level-Logik.

Eine dünne Wrapper-Klasse (`R50kBpeTokenizer`) kapselt Library-Details und stabilisiert unsere API (`encode`, `decode`, `encodeOrdinary`).

==== Warum `r50k_base` in diesem Kapitel
"Ada" bezieht sich auf eines der ursprünglichen GPT-3-Modelle von OpenAI (Ada, Babbage, Curie, Davinci).
Für dieses Kapitel verwenden wir aus Performance- und Reproduzierbarkeitsgründen ein Ada-nahes Tokenizer-Setup auf Basis von `EncodingType.R50K_BASE`.

Wichtige Eckdaten:

* Encoding-Name: `r50k_base`
* Vokabulargröße: `50.257` Tokens
* Verwendet von: GPT-2, GPT-3 (`ada`, `babbage`, `curie`, `davinci`), `text-ada-001`

Wichtig: `vocabSize = 50.257` ist nur dann fachlich korrekt, wenn das aktive Encoding zur R50K-/P50K-Familie gehört.

==== Beispiel: Roundtrip mit bekanntem Text im BPE-Tokenizer

Ein erster Nachweis funktioniert auch beim BPE-Tokenizer über einen Roundtrip.
Der Unterschied zum `SimpleTokenizerV1`: Das Vokabular wird nicht aus einem `rawText` aufgebaut, sondern kommt bereits aus dem gewählten Encoding `r50k_base`.

[source,kotlin]
----
val tokenizer = R50kBpeTokenizer()
val text = "Hello, do you like tea?"
val ids = tokenizer.encode(text)
val decoded = tokenizer.decode(ids)

println("text: $text")
println("ids: $ids")
println("decoded: $decoded")
println("roundtrip.equal: ${decoded == text}")

check(ids.isNotEmpty())
check(decoded == text)
----

Interpretation:

* Das Encoding liefert eine nicht-leere Liste von Token-IDs.
* `decode(ids)` rekonstruiert wieder exakt den ursprünglichen Text.
* Der Roundtrip-Beweis funktioniert also auch mit dem BPE-Tokenizer.

==== Beispiel: Special Token als normaler Text

Ein zweiter Nachweis zeigt das Verhalten von `encodeOrdinary`.
Mit dieser Methode können Special-Token-Sequenzen als normaler Text behandelt werden.

[source,kotlin]
----
val tokenizer = R50kBpeTokenizer()
val text = "Hello, do you like tea? <|endoftext|>"
val ids = tokenizer.encodeOrdinary(text)
val decoded = tokenizer.decode(ids)

println("text: $text")
println("ids: $ids")
println("decoded: $decoded")
println("roundtrip.equal: ${decoded == text}")

check(decoded == text)
----

Interpretation:

* `encodeOrdinary` behandelt `<|endoftext|>` als normalen Text.
* Dadurch bleibt die Zeichenfolge beim Roundtrip unverändert erhalten.
* Das Verhalten unterscheidet sich bewusst von Tokenizern, die Special Tokens direkt als Steuerinformation interpretieren.

==== Beispiel: Unbekannte Wörter werden in Subwords zerlegt

Der wichtigste Unterschied zum `SimpleTokenizerV1` zeigt sich bei unbekannten Wörtern.
Der BPE-Tokenizer verwendet kein `UNKNOWN`-Token, sondern zerlegt unbekannte Wörter in bekannte Subwords beziehungsweise Byte-Sequenzen.

[source,kotlin]
----
val tokenizer = R50kBpeTokenizer()
val text = "Akwirw ier someunknownPlace"
val ids = tokenizer.encodeOrdinary(text)
val decoded = tokenizer.decode(ids)

println("text: $text")
println("ids: $ids")
println("decoded: $decoded")
println("roundtrip.equal: ${decoded == text}")
println("tokenCount: ${ids.size}")

check(ids.isNotEmpty())
check(decoded == text)
----

Interpretation:

* Auch Kunstwörter wie `Akwirw` oder `someunknownPlace` können encodiert werden.
* Es gibt kein Fallback auf ein einzelnes `UNKNOWN`-Token.
* Stattdessen erzeugt das BPE-Encoding mehrere bekannte Teil-Tokens, die sich beim Decodieren wieder korrekt zusammensetzen lassen.

Damit ist der qualitative Unterschied zwischen beiden Tokenizer-Arten klar sichtbar:

* `SimpleTokenizerV1` mappt unbekannte Wörter auf `UNKNOWN`.
* `R50kBpeTokenizer` zerlegt unbekannte Wörter in bekannte Subwords.


[IMPORTANT]
====
Für den weiteren Verlauf des Buchs nutzen wir zwei klar getrennte Rollen:

* `SimpleTokenizerV1` dient als didaktischer Einstieg, um Tokenisierung, Vokabularaufbau und `UNKNOWN`-Mapping transparent zu verstehen.
* `R50kBpeTokenizer` ist der kanonische Ausführungspfad für die folgenden Kapitel, weil er das reale BPE-Encoding (`r50k_base`) über JTokkit bereitstellt.

Ab den nachfolgenden Kapiteln referenzieren wir deshalb primär den `R50kBpeTokenizer`.
Die Scratch-Variante bleibt als konzeptionelle Referenz erhalten, wird aber nicht parallel als zweiter Hauptpfad fortgeführt.
