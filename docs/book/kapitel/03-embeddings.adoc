[[Embeddings]]
== Embeddings

Ein Tokenizer liefert diskrete Token-IDs.
Damit ein neuronales Netz mit diesen Tokens rechnen kann, müssen die IDs in kontinuierliche Vektoren überführt werden.
Diese Vektoren heißen Embeddings.

[IMPORTANT]
====
Für den weiteren Verlauf des Buchs trennen wir zwei Rollen klar:

* Die einfachen, nicht trainierbaren Embedding-Varianten dienen dem didaktischen Verständnis der Mechanik.
* Für den Trainingspfad verwenden wir trainierbare Embeddings, bei denen Gewichte über `backward` und `step` aktualisiert werden.

Ab den nachfolgenden Kapiteln orientieren sich die Beispiele daher primär am trainierbaren Ausführungspfad.
====

=== Warum Embeddings?

Eine reine Token-ID wie `342` ist für ein Modell zunächst nur ein diskreter Index.
Die Zahl selbst trägt keine Bedeutung darüber, ob das Token ein Verb, ein Name oder ein Satzzeichen ist.

Embeddings lösen dieses Problem, indem jede Token-ID auf einen Vektor fester Länge abgebildet wird.
Damit wird aus einem diskreten Symbol ein kontinuierlicher Punkt im Vektorraum.
Auf diesem Raum kann das Modell mit linearen Algebra-Operationen arbeiten.

Dadurch werden Beziehungen zwischen Tokens numerisch nutzbar:

* ähnliche Tokens können im Vektorraum nah beieinander liegen
* unterschiedliche Tokens liegen weiter auseinander
* das Modell lernt diese Struktur während des Trainings automatisch

Wichtig: Diese Nähe ist nicht „von Hand“ vorgegeben.
Sie entsteht durch den Trainingsprozess, weil das Modell in vielen Kontexten lernt,
welche Token ähnliche Rollen übernehmen und welche nicht.

=== Token Embedding

Ein Token Embedding ist eine Matrix der Form `vocabSize x embeddingDim`.
Jede Zeile gehört zu einer Token-ID.
Beim Forward-Pass wird per Lookup die passende Zeile gelesen.

In der Praxis bedeutet das:

* `vocabSize` bestimmt, wie viele unterschiedliche Token-Zeilen es gibt
* `embeddingDim` bestimmt, wie viele numerische Freiheitsgrade pro Token verfügbar sind

Ist `embeddingDim` zu klein, kann das Modell nur grobe Beziehungen abbilden.
Ist `embeddingDim` sehr groß, steigen Speicher- und Rechenkosten deutlich.
Die Wahl ist daher immer ein Trade-off zwischen Ausdrucksstärke und Effizienz.

=== Positional Embedding

Self-Attention ist ohne Zusatzinformation positions-invariant.
Positional Embeddings liefern daher einen zweiten Vektor, der die Position eines Tokens (`0, 1, 2, ...`) kodiert.

Ohne Positionsinformation sähe das Modell nur eine Menge von Tokens,
nicht aber deren Reihenfolge im Satz.
Für Sprache ist Reihenfolge jedoch zentral, weil Grammatik und Bedeutung davon abhängen.

Positional Embeddings sind daher keine optionale Verfeinerung,
sondern eine notwendige Information, damit ein Transformer Sequenzen statt bloßer Token-Mengen verarbeitet.

=== Input Embedding

Der finale Eingabevektor für das Modell entsteht aus:

`InputEmbedding = TokenEmbedding(tokenId) + PositionalEmbedding(position)`

Beide Vektoren müssen dieselbe Dimension besitzen.
Erst dieser kombinierte Vektor geht in die erste Attention-Schicht.

Semantisch kann man die Summe so lesen:

* Token Embedding beantwortet: „Was ist das für ein Token?“
* Positional Embedding beantwortet: „Wo steht es in der Sequenz?“

Das Input Embedding trägt damit beide Informationen gleichzeitig.
Diese kombinierte Darstellung ist die eigentliche Eingabe,
auf der dann Query/Key/Value-Projektionen und Attention aufsetzen.

=== Implementierung: Trainable Token Embedding

Für den trainierbaren Pfad verwenden wir `TrainableTokenEmbedding`.
Das Grundprinzip:

* `forward(tokenIds)`: liefert die aktuellen Embedding-Vektoren
* `backward(gradOutput)`: akkumuliert Gradienten für die im Forward genutzten Token-Zeilen
* `step(learningRate)`: aktualisiert die Gewichte (`weights -= lr * grad`)

Der wichtige Unterschied zu einer nicht-trainierbaren Lookup-Tabelle (link:{sourceDirKapitel2}/scratch/TokenEmbedding.kt[`TokenEmbedding`]) ist hier der Rückkanal:
Die Embedding-Zeilen werden nicht nur gelesen, sondern über Gradienten aktiv angepasst.
Damit lernen häufig gemeinsam auftretende Token über viele Schritte hinweg eine nützliche Geometrie im Vektorraum.

=== Aufbau der Klasse

Die Klasse `TrainableTokenEmbedding` besteht aus drei logischen Blöcken:

* **Parameter und Gewichte:** `vocabSize`, `embeddingDim`, initialisierte Matrix `weights`
* **Trainingszustand:** Gradientenspeicher `grad` und gemerkte `lastTokenIds`
* **Trainingsschritte:** `forward`, `backward`, `step`, `zeroGrad`

Damit ist der gesamte Lebenszyklus eines trainierbaren Embeddings in einer Klasse abgebildet: lesen, Gradienten sammeln, Gewichte aktualisieren.

=== Gewichte und Initialisierung

`weights` ist eine Matrix der Form `vocabSize x embeddingDim`.
Jede Zeile repräsentiert ein Token-Embedding.

Die Initialisierung erfolgt zufällig mit einer Skalierung `1/sqrt(embeddingDim)`.
So starten die Werte klein genug, damit das Training stabiler anlaufen kann.

=== Die Methode `backward()`

`backward(gradOutput)` erwartet einen Gradienten mit derselben Form wie die Forward-Ausgabe (`seqLen x embeddingDim`).
Für jede Position in der Sequenz wird der Gradient auf die korrespondierende Token-Zeile in `grad` akkumuliert.

Im Detail passiert in `backward()` Folgendes:

1. **Formprüfung**
   Es wird geprüft, ob `gradOutput.shape[0] == lastTokenIds.size` und
   `gradOutput.shape[1] == embeddingDim` gilt.
   Nur dann passt der Gradient zur Forward-Ausgabe.

2. **Positionsweises Zurückschreiben**
   Für jede Sequenzposition `i` wird die zugehörige Token-ID aus `lastTokenIds[i]` gelesen.
   Der Vektor `gradOutput[i, :]` wird dann auf genau diese Token-Zeile in `grad` addiert.

3. **Akkumulation statt Überschreiben**
   Es gilt pro Dimension explizit:
   `grad[tokenId, d] = grad[tokenId, d] + gradOutput[i, d]`
   Dadurch sammeln sich Beiträge über mehrere Positionen im selben Schritt.

Kleines Beispiel mit mehrfach vorkommender Token-ID:

* `lastTokenIds = [3, 7, 3, 12]`
* Token `3` kommt an Position `0` und `2` vor
* Ergebnis nach `backward`: Zeile `grad[3, :]` enthält die Summe aus
  `gradOutput[0, :] + gradOutput[2, :]`

Genau diese Summe wird im nachfolgenden `step()`-Aufruf in ein größeres Update für Token `3` umgesetzt.

=== Die Methode `step()`

`step(learningRate)` führt ein SGD-Update durch:

* `weights[v, d] = weights[v, d] - learningRate * grad[v, d]`

Danach wird `zeroGrad()` aufgerufen, damit der nächste Trainingsschritt mit frischen Gradienten startet.

Im Detail passiert in `step()` Folgendes:

1. **Alle Parameterzellen werden durchlaufen**
   Die Methode iteriert über alle Zeilen `v` und Dimensionen `d` der Embedding-Matrix.

2. **Gradientenabstieg je Zelle**
   Pro Zelle wird der aktuell akkumulierte Gradient angewendet:
   `weights[v, d] <- weights[v, d] - learningRate * grad[v, d]`.

3. **Reset für den nächsten Schritt**
   Nach dem Update wird der Gradientenspeicher zurückgesetzt, damit keine Altwerte in die nächste Iteration hineinlaufen.

Kleines Rechenbeispiel:

* `weights[3,0] = 0.50`
* `grad[3,0] = 2.00`
* `learningRate = 0.01`

Dann gilt:

* `weights[3,0] = 0.50 - 0.01 * 2.00 = 0.48`

Interpretation:

* positives `grad` verkleinert den Parameterwert
* negatives `grad` vergrößert den Parameterwert
* die Lernrate skaliert die Schrittweite

=== Die Methode `zeroGrad()`

`zeroGrad()` setzt den Gradientenspeicher auf Null zurück.
Das verhindert, dass alte Gradienten ungewollt in den nächsten Schritt hineinlaufen.

Warum ist das wichtig?

* `backward()` akkumuliert Beiträge in `grad`.
* Ohne Reset würden Beiträge aus älteren Iterationen zusätzlich in spätere Updates einfließen.
* Das würde den beabsichtigten Lernschritt pro Iteration verfälschen.

Der typische Zyklus ist daher:

1. `forward(...)`
2. `backward(...)`
3. `step(learningRate)`
4. `zeroGrad()` (hier im `step()` bereits integriert)

Hinweis:
In dieser Implementierung ruft `step()` intern bereits `zeroGrad()` auf.
Deshalb ist ein zusätzlicher externer `zeroGrad()`-Aufruf unmittelbar danach nicht notwendig.

=== Implementierung: Trainable Position Embedding

Ja, in GPT-2-artigen Architekturen sind Positionsvektoren trainierbar.
Auch hier gibt es also eine Gewichtsmatrix, diesmal jedoch der Form `contextLength x embeddingDim`.

Der Unterschied zum Token Embedding liegt nur in der Bedeutung der Zeilen:

* beim Token Embedding steht jede Zeile für eine Token-ID
* beim Positional Embedding steht jede Zeile für eine Position in der Sequenz

Für den trainierbaren Pfad verwenden wir deshalb `TrainablePositionalEmbedding`.
Das Grundprinzip ist analog zu `TrainableTokenEmbedding`:

* `forward(sequenceLength)`: liefert Positionsvektoren für `0 until sequenceLength`
* `backward(gradOutput)`: akkumuliert Gradienten auf den verwendeten Positionszeilen
* `step(learningRate)`: aktualisiert die Positionsgewichte

=== Aufbau der Klasse `TrainablePositionalEmbedding`

Die Klasse `TrainablePositionalEmbedding` besteht ebenfalls aus drei logischen Blöcken:

* **Parameter und Gewichte:** `contextLength`, `embeddingDim`, initialisierte Matrix `weights`
* **Trainingszustand:** Gradientenspeicher `grad` und gemerkte `lastPositions`
* **Trainingsschritte:** `forward`, `backward`, `step`, `zeroGrad`

Der Unterschied zur Token-Variante besteht also nicht im Trainingsmechanismus,
sondern nur darin, dass Positionen statt Token-IDs adressiert werden.

=== Gewichte und Initialisierung für Positionen

`weights` ist eine Matrix der Form `contextLength x embeddingDim`.
Jede Zeile repräsentiert das Embedding einer Position.

Die Initialisierung erfolgt ebenfalls zufällig mit der Skalierung `1/sqrt(embeddingDim)`.
Dadurch starten die Positionsvektoren klein und können im Training schrittweise lernen,
welche Positionsmuster für das Modell nützlich sind.

=== Implementierung: Trainable Input Embedding

Das Input Embedding selbst ist in diesem Aufbau **kein eigener trainierbarer Parameterblock**.
Es ist das Ergebnis der Addition aus zwei bereits trainierbaren Komponenten:

* `TrainableTokenEmbedding`
* `TrainablePositionalEmbedding`

Formal gilt weiterhin:

`InputEmbedding = TokenEmbedding + PositionalEmbedding`

Trainiert werden also die beiden Quellmatrizen.
Das Input Embedding ist die abgeleitete Zwischendarstellung, die daraus pro Sequenz berechnet wird.

Konzeptionell bedeutet das:

* Tokenvektoren lernen semantische Information
* Positionsvektoren lernen Reihenfolgeninformation
* das Input Embedding kombiniert beides zur Eingabe für die Attention-Schicht

Ein separates `TrainableInputEmbedding` wäre nur dann nötig,
wenn du zusätzlich eigene Parameter auf dieser Summendarstellung modellieren möchtest.

=== Aufbau der Klasse `TrainableInputEmbedding`

Die Klasse `TrainableInputEmbedding` kapselt die beiden trainierbaren Teilkomponenten
und stellt sie als eine gemeinsame Schnittstelle für den restlichen Modellpfad bereit.

Die drei Kernaufgaben sind:

* **Forward:** Token- und Positionsvektoren berechnen und addieren
* **Backward:** denselben Gradienten an beide Teilkomponenten weiterreichen
* **Step/Reset:** Optimizer-Update und Gradienten-Reset für beide Komponenten ausführen

=== Design-Entscheidungen

* **Trainierbarer Hauptpfad:** Für den restlichen Buchverlauf setzen wir auf trainierbare Embeddings.
* **Klarer API-Dreiklang:** `forward`, `backward`, `step` bildet den Trainingsablauf explizit ab.
* **Didaktischer Parallelpfad:** Nicht-trainierbare Varianten bleiben als Lernhilfe erhalten, aber nicht als Hauptpfad.
* **Einfache SGD-Logik:** Das Update bleibt transparent und nachvollziehbar.
* **Trainierbare Positionsvektoren:** Für den gewählten GPT-2-artigen Pfad behandeln wir Positionsvektoren als lernbare Parameter.
* **Komposition statt Monolith:** `TrainableInputEmbedding` delegiert an Token- und Positional-Komponente statt deren Logik zu duplizieren.

=== Stolpersteine

* **Sparse-Update-Charakter:** Nur im Forward verwendete Token-Zeilen erhalten Gradienten.
* **Mehrfach vorkommende Tokens:** Gradienten derselben Token-ID summieren sich auf.
* **Formprüfungen im Backward:** `gradOutput` muss zur Forward-Ausgabe passen (`seqLen x embeddingDim`).
* **Skalierung:** Bei großem Vokabular können vollständige Matrix-Updates ineffizient werden.
* **Positionsgrenze:** `sequenceLength` darf `contextLength` nicht überschreiten.
* **Gradientenweitergabe verstehen:** Bei `input = token + position` wird derselbe `gradOutput` bewusst an beide Teilkomponenten weitergereicht.
