== Attention & Multi-Head Attention

Der Attention-Mechanismus ist das Herzstück eines Transformers: Er erlaubt
es jedem Token, sich auf alle anderen Token der Sequenz zu "beziehen" und
so Kontext herzustellen.

=== Warum Attention?

Im letzten Kapitel haben wir gesehen, wie aus Token-IDs Vektoren werden.
Jeder Token bekommt dadurch eine numerische Darstellung. Diese Darstellung ist
aber zuerst lokal: Sie beschreibt den Token und seine Position, noch nicht seine
Rolle im ganzen Satz.

Sprache funktioniert selten wortweise. Ein Wort bekommt seine Bedeutung oft erst
durch andere Wörter in der Nähe. In dem Satz "Die Bank am Fluss war nass" meint
"Bank" etwas anderes als in "Die Bank genehmigt den Kredit". Das Token allein
reicht nicht; der Kontext entscheidet.

Attention ist der Mechanismus, mit dem ein Modell diesen Kontext bildet. Für
jede Position fragt das Modell: Welche anderen Positionen sind gerade wichtig?
Die Antwort ist keine harte Auswahl. Stattdessen verteilt Attention Gewichte
über die Sequenz. Manche Tokens bekommen viel Gewicht, andere wenig.

Das Ergebnis ist ein neuer Vektor pro Token. Dieser Vektor enthält weiterhin die
Information des aktuellen Tokens, ist aber mit relevanten Informationen aus dem
Kontext angereichert.

=== Die Grundidee intuitiv

Stell dir vor, jedes Token schaut auf die ganze Sequenz und sammelt Hinweise.
Dabei passieren drei Dinge:

* Es formuliert eine Frage: Wonach suche ich gerade?
* Es vergleicht diese Frage mit den Rollen der anderen Tokens.
* Es übernimmt die Inhalte der Tokens, die gut zur Frage passen.

Aus diesen drei Rollen entstehen Query, Key und Value.

Eine **Query** ist die Suchfrage eines Tokens. Sie beschreibt, welche Art von
Information für diese Position nützlich wäre.

Ein **Key** ist das Vergleichssignal eines Tokens. Er beschreibt, wofür dieses
Token im Kontext angeboten wird.

Ein **Value** ist der Inhalt, der weitergegeben wird, wenn Query und Key gut
zusammenpassen.

Damit trennt Attention drei Aufgaben, die bei Sprache alle gleichzeitig wichtig
sind: suchen, vergleichen und Information übernehmen.

=== Gewichtete Kontextbildung

Für jedes Token vergleicht Attention seine Query mit den Keys aller Tokens.
Daraus entstehen Gewichte. Ein hohes Gewicht bedeutet: Dieser andere Token ist
für die aktuelle Position wichtig. Ein niedriges Gewicht bedeutet: Dieser Token
spielt hier kaum eine Rolle.

Anschließend werden die Values mit diesen Gewichten gemischt. Das ist wie eine
gewichtete Zusammenfassung der Sequenz aus Sicht einer bestimmten Position.

Wichtig ist: Jede Position bekommt ihre eigene Zusammenfassung. Das erste Token
kann also auf andere Wörter achten als das dritte Token. Genau dadurch entstehen
kontextabhängige Repräsentationen.

=== Warum Multi-Head Attention?

Ein einzelner Attention-Blick kann nur eine gelernte Art von Beziehung besonders
gut abbilden. Sprache enthält aber viele Beziehungen gleichzeitig: Subjekt und
Verb, Adjektiv und Nomen, Pronomen und Bezug, lokale Nachbarschaft und längere
Abhängigkeiten.

Multi-Head Attention löst das, indem mehrere Attention-Köpfe parallel arbeiten.
Jeder Kopf bekommt eigene gelernte Projektionen und kann dadurch eine andere
Perspektive auf dieselbe Sequenz entwickeln.

Man kann sich die Köpfe wie mehrere Leser vorstellen, die denselben Satz mit
unterschiedlichem Fokus lesen. Einer achtet vielleicht auf grammatische Nähe,
ein anderer auf semantische Rollen, ein weiterer auf spätere oder frühere
Positionen. Am Ende werden diese Perspektiven wieder zusammengeführt.

Der Nutzen liegt nicht darin, dass wir jedem Kopf manuell eine feste Aufgabe
geben. Die Aufgaben entstehen im Training. Multi-Head Attention gibt dem Modell
nur genügend getrennte Blickwinkel, um verschiedene Muster gleichzeitig zu
lernen.

=== Technisches Konzept: Scaled Dot-Product Attention Schritt für Schritt

Das technische Konzept übersetzt die Intuition (suchen, vergleichen, übernehmen)
in sechs aufeinanderfolgende Rechenschritte:

- Projektion,
- Ähnlichkeitsvergleich,
- Skalierung,
- Maskierung,
- Normalisierung und gewichtete Summe.

Eine optionale Trainingsregularisierung wird später im Ablauf eingeordnet.

==== 1. Lineare Projektionen (Q, K, V)

Die Eingabe ist eine Matrix `X` der Form `[ctx, embeddingDim]`. Jede Zeile
repräsentiert ein Token `x_i`. Damit das Modell lernen kann, wonach ein Token
sucht und wofür es steht, wird `X` durch drei trainierbare Gewichtsmatrizen
`W_Q`, `W_K` und `W_V` projiziert:

[source,text]
----
Q = X @ W_Q    // Query-Matrix  [ctx, headDim]
K = X @ W_K    // Key-Matrix    [ctx, headDim]
V = X @ W_V    // Value-Matrix  [ctx, headDim]
----

Für ein einzelnes Token `i` bedeutet das:

* `Q_i` beschreibt die aktuelle Suchfrage an die Sequenz.
* `K_i` beschreibt das Signal, das dieses Token anderen Suchfragen anbietet.
* `V_i` enthält den eigentlichen Inhalt, der bei hoher Übereinstimmung weitergegeben wird.

==== 2. Ähnlichkeit messen: Das Skalarprodukt (Dot-Product)

Um zu messen, wie gut die Frage von Token `i` zum Angebot von Token `j` passt,
berechnen wir das Skalarprodukt `Q_i · K_j`. Über alle Tokens hinweg passiert
das als Matrixmultiplikation `Q @ K^T`:

[source,text]
----
scores = Q @ K^T    // Matrix der Form [ctx, ctx]
----

Der Eintrag `scores[i, j]` misst die Ähnlichkeit zwischen Query `i` und Key `j`.
Ein höherer (positiverer) Wert bedeutet höhere Relevanz: Ein hoher positiver Score
führt nach dem Softmax zu einem Gewicht nahe `1.0` (starke Aufmerksamkeit),
ein Wert um `0` bedeutet neutrale Relevanz, und stark negative Werte (oder `-∞`)
führen zu einem Gewicht von nahe `0.0` (keine Aufmerksamkeit).

==== 3. Skalierung mit √d_k

Warum dividieren wir das Skalarprodukt durch `√d_k`?

Nehmen wir an, die Komponenten von Query `Q_i` und Key `K_j` sind unabhängig verteilte Zufallsvariablen mit Mittelwert `0` und Varianz `1`. Das Skalarprodukt bildet die Summe über `d_k` Produkte:

[source,text]
----
Q_i · K_j = Σ_{h=1}^{d_k} Q_{i,h} * K_{j,h}
----

Jedes einzelne Produkt `Q_{i,h} * K_{j,h}` hat ebenfalls Mittelwert `0` und Varianz `1`. Da sich bei der Summe unabhängiger Zufallsvariablen die Varianzen addieren, hat das unskalierte Skalarprodukt eine Varianz von `d_k` und eine Standardabweichung von `√d_k`.

Das bedeutet: Je größer die Head-Dimension `d_k` ist, desto weiter streuen die berechneten Scores betragsmäßig nach oben und unten. Bei `d_k = 64` beträgt die Standardabweichung bereits `8`. Ein Score kann dann leicht Werte von `+16` oder `-16` annehmen.

Verhalten im Softmax ohne Skalierung:

* Ein extremer Score wie `+16` erzeugt im Softmax `exp(16) ≈ 8.886.110`.
* Selbst ein leicht kleinerer Score von `+8` erzeugt nur `exp(8) ≈ 2.980`.
* Der höchste Score dominiert dadurch die Softmax-Verteilung fast vollständig (Spitzenbildung / One-Hot-Verhalten).
* Die Ableitung der Softmax-Funktion geht in diesen extremen Bereichen gegen `0` (vanishing gradient). Das Modell kann seine Gewichte kaum noch über Backpropagation anpassen.

Durch die Division durch `√d_k`:

[source,text]
----
scaled_scores = (Q @ K^T) / √d_k
----

wird die Varianz des Ergebnisses wieder auf exakt `1.0` normiert. Die Scores bleiben moderat, die Softmax-Verteilung bleibt differenzierbar, und der Gradientenfluss während des Trainings ist stabilisiert.

==== 4. Maskierung (Causal Masking für Sprache)

In autoregressiven Sprachmodellen erzeugt das Modell Text Token für Token.
Token `i` darf beim Lernen und Generieren keine Information aus zukünftigen
Positionen `j > i` nutzen.

Deshalb werden vor dem Softmax alle Eintrags-Positionen `j > i` in den Scores auf
`-∞` gesetzt:

[source,text]
----
if (j > i) scaled_scores[i, j] = -∞
----

Da `exp(-∞) = 0` ist, erhalten zukünftige Positionen im nächsten Schritt ein
Gewicht von exakt `0`. Position `i` sieht somit nur sich selbst und alle
vorherigen Tokens `0 .. i`.

==== 5. Normalisierung mit Softmax

Die skalierten (und eventuell maskierten) Scores sind noch beliebige reelle Zahlen. Um sie als Aufmerksamkeitsgewichte für eine gewichtete Summe zu nutzen, müssen sie in Wahrscheinlichkeiten umgewandelt werden. Dafür wenden wir zeilenweise die Softmax-Funktion an:

[source,text]
----
weights = softmax(scaled_scores)    // Zeilenweise über Key-Spalten j
----

Für jedes Token `i` berechnet der Softmax für jede Key-Position `j`:

[source,text]
----
weights[i, j] = exp(scaled_scores[i, j]) / Σ_{k=0}^{ctx-1} exp(scaled_scores[i, k])
----

Warum ist Softmax hier die richtige Wahl?

1. **Exponentiation `exp(x)`:** Wandelt jeden Score in einen positiven Wert um (`exp(x) > 0`). Damit wird kein Gewicht negativ, selbst wenn der ursprüngliche Score stark negativ war. Zukünftige maskierte Positionen mit `-∞` werden zu exakt `exp(-∞) = 0.0`.
2. **Normalisierung durch die Summe:** Die Division durch die Summe aller Exponenten garantiert, dass die Summe aller Gewichte in Zeile `i` exakt `1.0` (also `100%`) ergibt: `Σ_j weights[i, j] = 1.0`.
3. **Differenzierbarkeit:** Softmax ist eine stetig differenzierbare Funktion. Das erlaubt es dem Modell, während des Backpropagation-Schritts Gradienten durch die Aufmerksamkeitsgewichte zurück zu den Query- und Key-Projektionen zu leiten.

Numerische Stabilität in der Praxis:

In der Praxis würde eine direkte Berechnung von `exp(score)` bei großen Scores zu einem numerischen Überlauf (`Double.POSITIVE_INFINITY` / Overflow) führen. Deshalb nutzt die Implementierung (siehe `Tensor.softmax()` / `TensorMultik.softmax()`) den sogenannten **Max-Trick**:

[source,text]
----
max_score = max(scaled_scores[i, :])
weights[i, j] = exp(scaled_scores[i, j] - max_score) / Σ_k exp(scaled_scores[i, k] - max_score)
----

Indem wir vor der Exponentiation das Zeilenmaximum `max_score` abziehen, ist der größte Exponent exakt `exp(0) = 1.0`. Das mathematische Ergebnis bleibt dabei identisch, aber Überläufe werden zuverlässig verhindert.

Nach dem Softmax ist jede Zeile `i` der Matrix `weights` (Form `[ctx, ctx]`) eine gültige Wahrscheinlichkeitsverteilung. Sie beschreibt exakt, wie viel Prozent der Aufmerksamkeit Position `i` auf jede Position `j` der Sequenz richtet.

==== Optional: Attention-Dropout während des Trainings

Wenn `dropoutProb > 0.0` konfiguriert ist, wird Attention-Dropout **erst nach
dem Softmax** auf die Gewichte angewendet. Die Implementierungen aktivieren
diesen Schritt ausschließlich bei `training == true`:

[source,text]
----
if (training && dropoutProb > 0.0) {
    weights = weights.dropout(dropoutProb, rnd)
}
----

Bei `training == false` bleiben die Softmax-Gewichte unverändert. Dadurch bleibt
die Auswertung deterministisch; das gilt auch für die Generierung im
Evaluierungsmodus.

==== 6. Kontext bilden (Gewichtete Summe der Values)

Im letzten Schritt werden die Wichtigkeitsgewichte mit den Inhalten `V` multipliziert:

[source,text]
----
output = weights @ V    // Matrix der Form [ctx, headDim]
----

Für jede Position `i` entsteht ein Vektor:

[source,text]
----
output_i = Σ_j weights[i, j] * V_j
----

Dieser Vektor ist das Ergebnis von Scaled Dot-Product Attention für eine Position:
Eine gewichtete Kombination aller Value-Vektoren in Abhängigkeit davon, wie gut
deren Keys zur Query gepasst haben.

=== Shape-Herleitung & Tensor-Dimensionen

Die sechs Schritte haben zunächst den Rechenweg für einen einzelnen Head und
eine Query-Position gezeigt. Im Multi-Head-Forward werden diese Berechnungen
für alle `ctx` Positionen und für jeden Head ausgeführt. Anschließend werden
die Head-Ausgaben zusammengeführt und auf die Modell-Dimension
zurückprojiziert. Damit dieser Übergang von der Einzelberechnung zum gesamten
Tensor im Code nachvollziehbar bleibt, betrachten wir die Shapes nun
systematisch.

==== Verbindliche Tensor-Shape-Regeln

Alle Formen beziehen sich auf row-major `TensorMultik`-Daten (bzw. `Tensor` im Scratch-Pfad):

[cols="1,2,3", options="header"]
|===
| Bezeichnung | Form / Dimension | Bedeutung
| `input` | `[ctx, embeddingDim]` | Eingabezeilen pro Token (`ctx` Token-Vektoren)
| `W_Q`, `W_K`, `W_V` | `[embeddingDim, headDim]` | Gemeinsame Projektionsmatrizen
| `Q`, `K`, `V` | `[ctx, headDim]` | Projizierte Gesamtsequenz über alle Köpfe
| `headDim` | `numHeads * dK` | Gesamtbreite aller Köpfe kombiniert
| `Q_h`, `K_h`, `V_h` | `[ctx, dK]` | Projizierter Teil-Tensor für einen einzelnen Head $h$
| `scores_h` | `[ctx, ctx]` | Query-Position $i$ gegen Key-Position $j$ pro Head
| `weights_h` | `[ctx, ctx]` | Zeilenweise normalisierte Aufmerksamkeitsgewichte pro Head
| `headOutput_h` | `[ctx, dK]` | Gewichtete Value-Summen eines einzelnen Heads
| Konkatenierte Köpfe | `[ctx, headDim]` | Spaltenweise Zusammenführung aller `numHeads` Köpfe
| `W_output` | `[headDim, embeddingDim]` | Rückprojektion auf die Modell-Embedding-Dimension
| `output` (Rückgabe) | `[ctx, embeddingDim]` | Finale kontextualisierte Output-Sequenz
|===

Für jeden Forward-Aufruf gilt strikt `input.size == ctx * embeddingDim`. `ctx` ist die Sequenzlänge (Anzahl der Tokens) und nicht zu verwechseln mit `embeddingDim`, `dK` oder der Anzahl der Köpfe `numHeads`.

==== Herleitung pro Head und Beziehung zwischen `dK`, `headDim` und `embeddingDim`

Es ist essenziell, `dK` und `headDim` begrifflich und dimensional nicht gleichzusetzen:

* **`dK` (Head-Dimension):** Die innere Vektorbreite *eines einzelnen* Attention-Kopfes (z. B. $d_K = 64$).
* **`headDim` (Gesamt-Head-Breite):** Die Summe der Breiten aller Köpfe: `headDim = numHeads * dK` (z. B. Bei 8 Köpfen à 64 ergibt sich folgende Berechnung:
`headDim = 8 × 64 = 512`
* **`embeddingDim` (Modell-Dimension):** Die äußere Vektordimension des Modells (z. B. $512$).

In der kanonischen Implementierung `MultiHeadAttentionMultikTensor` ist `embeddingDim` **nicht** zwingend auf `numHeads * dK` beschränkt. Das Modell projiziert die Eingabe `[ctx, embeddingDim]` mit $W_Q, W_K, W_V$ der Form `[embeddingDim, headDim]` zunächst auf `headDim`. Nach der Head-Verarbeitung und Konkatenation (`[ctx, headDim]`) bringt die Output-Projektion $W_{\text{output}}$ der Form `[headDim, embeddingDim]` das Ergebnis wieder exakt auf die äußere Dimension `[ctx, embeddingDim]` zurück.

Falls `embeddingDim != numHeads * dK` gewählt wird (z. B. `embeddingDim = 768` bei `numHeads = 8` und `dK = 64` `-> headDim = 512`), decken die Eingangs- und Ausgangsprojektionen diesen Unterschied vollständig und mathematisch korrekt ab.

=== Optionaler Anschluss: Perplexity

Attention selbst berechnet keine Perplexity. Perplexity ist eine
Trainingsmetrik für ein Sprachmodell und wird aus der mittleren
Cross-Entropy (CE) über die vorhergesagten Zieltoken berechnet:

[source,text]
----
perplexity = exp(mean CE)
----

Eine niedrigere Perplexity bedeutet, dass das Modell die Zielsequenz im Mittel
mit höherer Wahrscheinlichkeit bewertet. Die Metrik gehört deshalb zum
Trainingspfad in Kapitel 05, nicht zur einzelnen Attention-Operation:

* `MultiHeadAttentionMultikTensor` liefert kontextualisierte Repräsentationen.
* Das nachgelagerte Sprachmodell berechnet daraus Logits und die
  Cross-Entropy.
* Erst aus dem Mittelwert dieser Loss-Werte wird Perplexity berechnet.

Dieser Anschluss setzt Training- und Validierungsmetriken voraus. Die
Trainingsinfrastruktur in Kapitel 05 berechnet daraus
`trainPerplexity = exp(trainLoss)` und
`validationPerplexity = exp(validationLoss)`. Bei Padding oder variabler
Sequenzlänge muss `mean CE` nur über gültige Zieltoken gebildet werden; sonst
ist die Perplexity nicht zwischen Batches vergleichbar.

=== Design-Entscheidungen

1. **Warum ist Causal Masking konfigurierbar?**
   - `causal = true` erzwingt autoregressive Self-Attention: Position `i` sieht keine Zukunft.
   - `causal = false` erlaubt bidirektionale Self-Attention über die ganze Sequenz.

2. **Warum Linear-Projektionen für Q/K/V?**
   - Ohne Projektionen müssten Q/K/V = Input-Embedding sein (weniger flexibel).
   - Mit Projektionen kann das Modell lernen, welche Aspekte wichtig sind.

3. **Warum nicht GQA oder MQA?**
   - Grouped Query Attention / Multi-Query Attention sparen Parameter, aber die
     Standard-Multi-Head-Form ist hier klarer didaktisch.

=== Stolpersteine & Tipps

1. **Dimension-Mismatch bei Matmul**
   - Q: (seq_len, head_dim), K^T: (head_dim, seq_len) → Scores: (seq_len, seq_len) ✅
   - Häufiger Fehler: K nicht transponiert → Dimension passt nicht ❌

2. **Softmax über falsche Achse**
   - Pro Query (Zeile) normalisieren, nicht über die ganze Matrix!
   - Richtig ist: Für jede Query-Zeile läuft die Summe über alle Key-Spalten
     derselben Zeile.

3. **Causal Mask Koordinaten**
   - Indizierung: Für 1D-Array als `[i * seq_len + j]`
   - Mask-Bedingung: `j > i` (Zukunft) blockieren, nicht `j >= i`!

4. **Gradient Flow durch Softmax**
   - Softmax ist nicht linear, aber seine Ableitung ist:
     `∂softmax(x_i) / ∂x_j = softmax_i * (delta_ij - softmax_j)`
   - Dies wird automatisch in `TensorMultik.backward()` berechnet.

=== Zusammenfassung

- **Scaled Dot-Product**: (Q · K^T) / √d_k, dann Softmax, dann @ V
- **Multi-Head**: Mehrere parallele Attention-Köpfe für reichere Repräsentation
- **Causal Masking**: Für autoregressive (token-by-token) Generierung
- **Backprop**: Gradienten fließen automatisch durch alle Tensor-Operationen
